# 效能地板(performance baseline)—— 與技術棧無關,第一天生效

> `security-baseline.md` 的雙生檔。**這一份是地板不是天花板**:全部與技術棧無關,
> 新專案第一天生效,不等「效能階段」。棧特定的手法寫在 `docs/stack-rules/<stack>.md`。
>
> 貫穿全檔的一條:**每條規則要寫得出執法點**(哪個設定 / 哪條 lint / 哪個 CI job /
> 哪支守衛)。寫不出執法點的,降級成「預設這樣做」,不准掛 P0 —— 規則沒有檢查一定會漂。

## §0 開工先寫:三個數字

在任何優化討論之前,先寫下這三個數字,它們是後面所有取捨的判準:

1. **p95 回應時間目標**(分開寫:讀路徑 / 寫路徑 / 背景任務)
2. **單一回應 payload 上限**(超過就要分頁或串流)
3. **單一請求允許的外呼次數上限**(DB query 數也算)

寫不出來 = 還不知道什麼叫「慢」,之後每次討論都會變成個人品味之爭。
這三個數字寫進 `CLAUDE.md` §2 或本檔,並且**進 CI 當門檻**(§10),不是牆上的標語。

## §1 量測先行(最常出錯的一族)

- [P0] **沒有 baseline 數字不准談優化**。「感覺慢」不是問題陳述;「p95 從 180ms 變 1.4s,
  在 X 之後」才是
- 🔴 **量測腳本自己會錯,而且是安靜的** —— 探針回的都是「看起來很正常的數字」。
  自檢要**陽性 + 陰性對照組**:陰性(應該量不到的)擋不住「探針整個沒跑」,
  陽性挑一個你確定存在的熱點,量不到就是量尺壞了
- [P0] **代理指標的輸出不是答案**:query 計數 / bundle 大小 / lint 統計是代理,
  報出去之前抽樣看實際請求或實際檔案
- [P0] 一面倒的結果特別可疑(全 0 / 每個端點同一個數字 / 六個模組量出一樣 = 量尺壞掉的訊號)
- [P1] **量測要可回查**:數字附「什麼環境 / 什麼資料量 / 什麼併發 / 量測日」。
  沒有這四項的數字,下次沒有人敢拿來比
- [P1] 生產要有**分位數**(p50/p95/p99)不是平均值;平均值會把一條 10 秒的尾巴藏起來

**執法點**:負載腳本進 repo(不是某人本機的一次性指令)· 關鍵端點的 p95 進 CI 門檻(§10)

## §2 資料存取(踩最多的一區)

- [P0] **N+1 防護**:批次載入 / dataloader / 正確 join。關聯載入是最常見瓶頸,
  而且在小資料量的 dev 環境**完全看不出來**
  - 執法點:測試裡 **assert query 數**(`n+1` 偵測套件或自己包 counter),
    不是靠 code review 看得出來
- [P0] **禁無上限查詢**。任何回傳列表的查詢都要有 limit;對外 API 一律 **cursor 分頁**
  (offset 分頁在深頁會退化,且資料變動時會漏/重複)
  - 執法點:repository 層守衛(無 limit 直接拋)+ grep 禁 `findAll()` 類無參數全表查
- [P0] **索引跟著查詢走**:每條熱路徑查詢指得出用哪條索引(看真的 EXPLAIN,不是推測)。
  複合索引的**欄位順序**要對得上 WHERE + ORDER BY
- [P0] **寫入路徑的索引成本也要算**:每多一條索引,每次寫入就多一次維護。
  只加「有查詢真的用到」的索引
- [P1] 交易**範圍越小越好**:交易裡禁做外呼(HTTP / 訊息佇列) —— 對方慢一秒,你的
  DB 連線就被佔一秒,連線池耗盡是這樣來的
- [P1] 讀寫分離 / 唯讀副本前,先確認你的程式碼**容忍得了複寫延遲**(寫完立刻讀會讀到舊值)
- [P1] 大量寫入走批次 / COPY,不要一列一個 round trip

**執法點**:測試 assert query count · migration review 要問「這條索引哪個查詢在用」

## §3 邊界、逾時與重試

- [P0] **每一個外呼都要有 timeout**。🔴 多數 HTTP client 的預設值是**無限等待** ——
  「沒設」不是「用預設的合理值」,是「賭對方永遠會回」
  - 執法點:禁用裸 client,只能用包好逾時的內部 wrapper;grep 守衛擋直接 new client
- [P0] **請求有總預算**:入口設一個 deadline 並一路傳遞下去,子呼叫不得超過剩餘預算。
  沒有總預算的系統,慢起來是**整條鏈一起卡住**
- [P0] **重試要有上限 + 指數退避 + 抖動**,且**只重試冪等操作**。
  無抖動的同步重試會製造自己的 DDoS(驚群)
- [P0] 非關鍵路徑掛掉時**核心功能照常**(AI / 搜尋 / 推薦 / 分析都屬於非關鍵):
  circuit breaker + 降級路徑,不是讓整頁轉圈
- [P1] 對外提交 / webhook / AI 動作帶 **idempotency key**(與 `security-baseline.md` §10 同一條)

**執法點**:client wrapper 是唯一入口 · 混沌測試把下游打掛一次,確認核心流程還活著

## §4 快取(失效比快取難)

- [P0] 🔴 **快取 key 必須含所有權限維度**(租戶 / 使用者 / 角色)。
  少一個維度就不是效能問題,是**跨租戶資料洩漏** —— 這條同時屬於 `security-baseline.md` §2
  - 執法點:快取 key 由集中的 builder 產生(禁手拼字串),builder 強制傳入 scope
- [P0] **先寫失效策略再寫快取**。寫不出「什麼時候失效」的快取不准上線
- [P1] **負快取**(查無結果也要快取一小段)否則不存在的 key 會每次打穿到 DB
- [P1] **驚群 / stampede**:熱 key 過期瞬間所有請求一起重算 —— 單飛(single-flight)或
  隨機化 TTL
- [P1] 快取命中率要**量得到**;量不到的快取沒有人知道它是不是根本沒在作用
- [P1] 分層要講清楚:CDN / 反向代理 / 應用內 / DB 各自快取什麼,同一份資料不要三層各有各的 TTL

## §5 Payload 與序列化

- [P0] **只回需要的欄位**。回應 DTO 明列欄位,禁直接把 DB entity 丟出去 ——
  同時是 over-fetch 洩漏防線(與 `security-baseline.md` 同一條)
- [P1] 大回應**串流**不要整包進記憶體(匯出 / 報表 / 檔案是典型)
- [P1] 壓縮打開,但別對已壓縮內容(圖片 / 影片)重複壓
- [P1] 序列化成本會被低估:巨大 JSON 的 encode/decode 本身就是熱點,量過再決定要不要換格式

## §6 熱路徑與冷路徑

- [P0] **重計算進背景 worker,不擋請求**。使用者按下去應該立刻拿到「已排入」,
  不是等 30 秒
- [P0] 背景任務要有**可觀測的狀態**(排隊中 / 執行中 / 失敗 / 可重試),
  否則使用者只會看到「沒反應」
- [P1] 開機預熱 vs 首次請求付代價:serverless / 容器冷啟動要納入 p95,不能只量暖機後的數字
- [P1] 啟動時做的事越少越好(schema 驗證除外 —— 那個要 fail-fast)

## §7 並發與資源上限

- [P0] **連線池上限 × 實例數 < DB 的最大連線數**。這個乘法沒算過的系統,
  擴容的那一天會整批連不上
- [P0] **fan-out 要有上限**:禁無上限併發(一次開 N 個 goroutine/promise/thread 打下游)。
  併發度是設定,不是資料量的函數
- [P0] **per-tenant 配額**(連線 / query 成本 / token / 請求數)防 noisy neighbor
- [P1] 背壓:佇列滿了要**拒絕**不是無限堆積;無界佇列 = 把延遲換成 OOM
- [P1] 記憶體:一次載入整張表 / 整個檔案的地方逐個列出來,問「資料量 ×10 會怎樣」

## §8 前端(有 UI 就適用)

- [P0] **bundle 預算進 CI**,超過就紅。沒有門檻的 bundle 只會單向長大
- [P0] 圖片給**明確尺寸**(擋 CLS)+ 適當格式與尺寸;字體用本地/預載(擋 FOUT + 擋外部請求)
- [P0] 四態分開(載入 / 空 / 錯誤 / 有資料) —— 「載入中」與「空的」長得一樣是真實的坑
- [P1] Core Web Vitals 門檻(LCP / INP / CLS)進 CI,且量**真實裝置等級**不是你的筆電
- [P1] 長清單虛擬化;禁在 render 裡重建物件當相依(讓 memo 全失效)
- [P1] 首屏只載首屏要的:路由層級分割,非關鍵功能延後載入

## §9 禁清單

無 timeout 的外呼 · 無上限的查詢 / fan-out / 佇列 · 交易裡做外呼 ·
不含租戶維度的快取 key · 直接回 DB entity · 迴圈裡發查詢(N+1) ·
無抖動的同步重試 · 只看平均值的效能報告 · 沒有失效策略的快取 ·
把「現況數字」寫死進註解當門檻(它必然過期,要寫規則不寫現況)

## §10 CI gates(全過才 merge)

- bundle 預算(有 UI)· 關鍵端點 p95 門檻 · 關鍵流程的 **query 數上限** assert ·
  無上限查詢守衛
- ⚠️ 「CI 有這條」要定期驗它**真的在跑**(job 0 step 沒 log = 沒開始跑,不是通過了)
- ⚠️ 門檻要寫**規則**不寫**現況**:`p95 < 300ms` 是規則;`p95 < 目前的 287ms` 是現況,
  下一次正常波動就會紅,然後被人調鬆到沒有意義
