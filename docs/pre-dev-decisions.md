# 開工前決策清單(pre-dev decisions)

> **用法**|新專案第一天,與人一起把這 24 格逐格填掉(或明確標「暫不決定+何時回來」)。
> 每一格都有一個真實專案的實證:**先定了受益,或後補付了代價**。
> 填完的答案寫進該專案的 `CLAUDE.md` / `AGENTS.md` —— 本檔是問題集,不是答案。

## 〇、定位(最先,因為它決定其餘一切的分母)

| # | 要決定的 | 若不先定的代價(實證) |
|---|---|---|
| 1 | **一句話定位 + 完整定位**;且**定位 ≠ MVP 範圍**,兩者不一致處逐項指得到一條裁定 | 「定位有而 MVP 沒有」每次都被當成漏掉,反覆重議已裁的事 |
| 2 | **清點的分母從哪來**:競品官方目錄 / 法規條文 / 客戶真實語料 —— 不是自己想的清單 | 自己寫的分母漏什麼,清單永遠顯示 100%(「忘記密碼」不在任何清單上,使用者按了才發現那條路不存在) |
| 3 | **不做清單 + 每條的理由**(禁令也要舉證) | 沒寫理由的「刻意不做」會被後人當成待補缺口翻案 |
| 4 | **第一個真實使用者是誰**,拿得到他的真實資料嗎 | 真實語料是所有設計的壓力測試分母(104 張真表打提案:83% 裝得下、第一列就裝不下) |

## 一、技術根(錯了要重寫的那幾格)

| # | 要決定的 | 代價實證 |
|---|---|---|
| 5 | **語言 / 框架 / 執行環境**,且評估**留痕**(對照表,不是結論一句話) | 三個月後「為什麼不用 X」答不出來就會重評一次 |
| 6 | **資料模型的根**:多租戶策略(RLS?)、金額型別(decimal 禁 float)、不可變資料(audit / 帳務) —— **第一天的事** | 租戶隔離事後補 = 重寫每一條查詢;float 存錢 = 對不上帳 |
| 7 | **授權政策**:OSS-only?商業授權預算?**授權查證方法論**:SPDX 欄位不可信(NOASSERTION / 附加條款不會出現在裡面)、一律讀 LICENSE **本文**、**禁競品條款可以推翻主授權**(它禁的動詞是 use-to-develop 不是 copy) | 三次地雷(自訂協議禁 no-code SaaS / 禁競品條款 / BSL 排除 embedded)都是讀本文才看到 |
| 8 | **fork vs 自研 + clean-room 邊界**。solo 做不了標準 clean room(讀了就污染,沒有第二個人)⇒ 判準是「**有沒有乾淨的替代來源**」:功能看官方文件、實作讀同類 MIT 專案(還能直接抄,比讀完自己想拿到更多) | — |
| 9 | **repo 形態**(monorepo?modular monolith?)+ **邊界執法工具**(dependency-cruiser / madge 進 CI,不靠自律) | 循環依賴檢查沒真的跑,一個月累積六條環 |
| 10 | **測試分層**:快層(單元)佔多數 · 關鍵流程對真 DB(testcontainers)· 瀏覽器走通即固化成 spec · **junit/json reporter 第一天就設**(紅燈的名字要活過你自己的 pipe) | 間歇紅的名字弄丟兩次,重跑全綠之後再也拿不回來 |

## 二、前端視覺(最容易「無聲漂移」的一區)

| # | 要決定的 | 代價實證 |
|---|---|---|
| 11 | **視覺規則的單一權威在哪一份** —— 自足(每個數字寫在裡面)、在版控、被 CI 盯;規則要人去開另一份稿才完整,那個規則就是不完整的 | 四層權威互相指、其中一層在 repo 外 ⇒ 每次動手先考古 |
| 12 | **母心智模型 / 參考系**:目標使用者腦中的畫面是什麼?競品要**實測**(活 DOM / 逐張截圖)不是印象;「競品沒有 X」是風險最高的句型,查不到就寫「未查證」 | 整條差異化論述建立在「競品 0 AI」上,一查全有 |
| 13 | **可稽核的視覺規則**(字級白名單 / 圓角角色 / 對比 AA 擋門)——數字不是形容詞;**「用」與「禁」都要舉證**,只要求一邊必然單向漂移 | 只有「太像 SaaS」一個失敗方向 ⇒ 漂到「太像內部後台」 |
| 14 | **mockup 制度**:稿是證據不是權威;每份稿標**身分**(提案/待落地/已落地/非現行/棄用/來源/競品);**落地了就更新稿**,別讓稿停在「提案」 | 拍板的設計在權威稿裡躺一個月,沒有任何路徑指向它,後人重寫了一套 |

## 三、工程紀律

| # | 要決定的 | 代價實證 |
|---|---|---|
| 15 | **規則與檢查同一個 commit**(反向也成立:CI 也會鎖住錯的規則) | 「規則寫了沒檢查」十次代價 |
| 16 | **出貨 DoD**:grep 呼叫端(「表/服務/端點/測試都在,就是沒有人呼叫它」型別檢查抓不到)· FMEA · 使用手冊節 | 六個模組三個底下是空的 |
| 17 | **CI 形態 + 「出貨前會跑的那一組」清單**。檢查存在 ≠ 會被跑:四種失效形狀(清單沒列它 / 沒人跑那份清單 / 名字指向的東西不存在 / **它從來沒有通過過**) | CI 靜默死一個月(job 0 step 沒 log);spec 寫完沒跑就 commit |
| 18 | **錯誤訊息給誰看**:使用者的句子(哪裡錯+怎麼做)與 API 的 code 分開;**fallback 回通用句不回原文** —— 最大破口不是缺對映,是 `return error.message` | validator 原文上畫面,而「看起來有處理」 |

## 四、協作方式(與 AI 助手的檔位,開工前就定)

| # | 要決定的 | 說明 |
|---|---|---|
| 19 | **回覆語言**(硬規則,無例外) | — |
| 20 | **授權邊界**:哪些動作自行執行、哪些逐次問(push / force push / prod / 對外發送) | 邊界會演化,但每一步要明文 |
| 21 | **「研究錨定的建議 = 已核准」的射程**:execution 檔位(每步確認 ↔ 一氣呵成)是開工前的決定;研究能推翻產品裁定,**不能推翻安全底線** | 中途反覆停下來問「要不要照做」是把做完的功課再走一次流程 |
| 22 | **全稱詞協議**:任務出現「100% / 全部 / 不要殘留」時,交付第一段是**拿原話逐句拆的差距表**,不是產出清單 | 兩次「100% 復刻」的缺口都是人抓到的,而交付報告每一項都是真的 |

## 五、知識制度

| # | 要決定的 | 代價實證 |
|---|---|---|
| 23 | **文件索引制度 + 「索引比權威舊」的防線**:自動載入的那一份(CLAUDE.md)最容易過期,而每一輪推理都據它;引數字前開權威檔 | 索引停在舊數字十輪 / 與權威差 30 項 |
| 24 | **記憶 / pitfall 制度**:量尺會安靜地錯是最大的一族(探針回「看起來很正常的數字」);pitfall 要寫成**可重跑的判別法**,不是敘事 | 單日探針錯十次的輪次不只一次;同一個坑寫下判別法後第二次三秒認出 |

---

## 附:反思的方法本身

這 24 格不是憑空想的 —— 產生它們的方法是:**回顧一個真實專案的每一次「決策方糾正」與每一條 pitfall,問「哪一個開工前的決定能讓這件事不發生」**。新專案跑三個月後,應該用同樣的方法回填本檔(哪幾格漏了、哪幾格是多餘的)。
