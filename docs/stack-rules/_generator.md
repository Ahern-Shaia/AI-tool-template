# 技術棧規則生成器規格(_generator)

> **用途**|某個技術棧在 `docs/stack-rules/` 沒有現成附件時,照本規格生成一份,
> 而不是自由發揮。固定維度 ⇒ 產出**可以對帳**(缺哪一維一眼看得到);
> 自由生成的規則沒有分母,等於沒查。
>
> **何時跑**|開工前決策(`pre-dev-decisions.md` §一 #5 語言/框架/執行環境)定案之後、
> 寫第一行業務碼之前。棧換了 / 主版本跳了也要重跑。
>
> **產出**|`docs/stack-rules/<stack>.md`,由**人 review 後才生效**。
> 生成物不是權威,review 過的才是。

## 一、動手前先查(輸入)

| # | 查什麼 | 怎麼查 |
|---|---|---|
| 1 | **實際的棧與版本**,不是口頭說的 | 讀 manifest 本文:`package.json` / `go.mod` / `pyproject.toml` / `Cargo.toml` / `pom.xml`;版本以鎖檔為準 |
| 2 | **部署形態** | 讀 Dockerfile / CI 設定那幾行:容器?serverless?長駐進程?worker 幾個? |
| 3 | **該棧既有的 linter 規則集** | 先看官方 / 主流嚴格集已經涵蓋什麼(大多數規則不用自己發明,只要**打開**) |
| 4 | **自家 repo 是否已有裁定** | grep 既有 design doc / AGENTS;上游已決定的不要重議 |
| 5 | **該棧的已知傷害面** | 官方 security 文件 + 該棧的常見 CVE 類型 + 該框架的「預設值陷阱」 |

🔴 **「本棧沒有 X」要附查法**:寫下「這個棧沒有對應機制」時,同一句附上怎麼查的
(哪份文件、哪個 grep)。兩種查法(精確名 + 寬鬆字根)不一致時,答案永遠是後者。

## 二、固定維度清單(缺一維不准交)

每一維**必須**有結論,三種合法結論:①一條規則 ②「本棧由 X 機制內建涵蓋」+ 指出是什麼
③「本棧不適用」+ 一句為什麼。**留白不是結論。**

### 安全維度(對齊 `security-baseline.md`)

| # | 維度 | 這一棧要回答的 |
|---|---|---|
| S1 | 注入 | 參數化查詢怎麼寫?動態 identifier 怎麼白名單?哪個 API 是拼字串的陷阱? |
| S2 | 反序列化 / 動態求值 | 有沒有 `eval` / `pickle` / 不安全 YAML / 物件反序列化這類洞? |
| S3 | 輸入邊界驗證 | HTTP body / env / DB row 進來時用什麼驗?型別系統管不到的邊界在哪? |
| S4 | 授權執法點 | 框架的哪一層做 authz?最容易繞過去的路徑是什麼(公開端點誤以為私有)? |
| S5 | Secret 與設定 | 怎麼載入與驗證?哪個命名慣例會把 secret 送上前端(如 `NEXT_PUBLIC_`)? |
| S6 | 錯誤與日誌外洩 | 預設會不會把 stack trace / SQL 原文吐給 client?怎麼關? |
| S7 | 相依與供應鏈 | 鎖檔怎麼鎖?安裝腳本怎麼關?`audit --prod` 對應指令是什麼? |
| S8 | 平台特有陷阱 | 這個框架**預設值**會傷人的地方(預設開啟的偵錯端點、預設無上限、預設信任 header) |

### 效能維度(對齊 `performance-baseline.md`)

| # | 維度 | 這一棧要回答的 |
|---|---|---|
| P1 | N+1 與批次載入 | ORM/資料層怎麼產生 N+1?怎麼在測試裡 assert query 數? |
| P2 | 分頁與上限 | cursor 分頁怎麼做?哪個 API 是「無上限全表查」的陷阱? |
| P3 | 逾時與取消 | 逾時怎麼設?**預設值是不是無限**?取消訊號怎麼一路傳遞? |
| P4 | 並發模型與上限 | 執行緒 / 協程 / 事件迴圈是哪一種?怎麼擋無上限 fan-out?什麼操作會阻塞它? |
| P5 | 連線池與資源 | 池的設定在哪?池上限 × 實例數怎麼算?什麼東西忘了關會洩漏? |
| P6 | 記憶體與資料量 | 哪些 API 會整包載入記憶體?串流的對應寫法是什麼? |
| P7 | 快取 | 慣用的快取層是什麼?key builder 怎麼強制帶 scope? |
| P8 | 建置與啟動 | 冷啟動成本?bundle / 二進位大小門檻?啟動時做了什麼可以延後? |

## 三、產出格式(硬性)

**每條規則兩件事不可省:規則本身 + 執法點。** 緊湊寫成一行也可以,但兩者都要在:

```
- [P0] 規則一句話(祈使句) —— 傷害是什麼(具體,不是「不安全」)
  · 執法點:哪個設定旗標 / 哪條 lint 規則 / 哪個 CI job / 哪支 grep 守衛
```

**出處**寫在檔頭的「來源與查證狀態」區塊(哪幾份官方文件 / 規則集 + 查證日),
不逐條重複;只有**爭議性或反直覺**的規則才逐條附連結與逐字引用。
🔴 **沒有真的去查就寫「待回查」**,不要寫一個看起來查過的日期 ——
查證狀態造假比沒查更貴,因為後人不會再查一次。
lint 規則 ID 會隨版本改名,採用前對著**專案實際安裝的版本**確認一次。

分級:**P0 = CI 擋** · **P1 = review 擋** · **P2 = 慣例**。
🔴 **寫不出執法點的不准掛 P0**,降級成 P2「預設這樣做」。
只寫禁令不寫執法,一個月後就是「規則寫了沒檢查」——這個 repo 為它付過十次代價。

檔尾**必須**有一節 **`## CI-fail 禁令清單`**:把所有 P0 壓成一行一條的可掃描清單
(形狀見 `typescript-nestjs.md` 檔尾)。那一節是給 CI 設定的人看的,不是給讀者看的。

## 四、禁止事項

- ❌ **禁沒有出處的「業界最佳實踐」**。查不到出處的降級成 P2 並標「未查證」
- ❌ **禁通用廢話**(「要注意效能」「做好錯誤處理」)—— 每條規則要指得出**這個棧的哪個 API**
- ❌ **禁把地板抄一遍**。`security-baseline.md` / `performance-baseline.md` 已說的,
  這裡只寫「在這個棧上長什麼樣」,不重述
- ❌ **禁在產出物裡標注違規**(「這條先簡化」+ 註解)—— 比忘記更糟,它讓違規看起來已處理。
  兩條路:寫好,或整條拿掉並在框外說明
- ❌ **禁憑記憶寫版本行為**。預設值會隨主版本改,一律回查當前版本文件

```
| 維度 | 結論 | 執法點 |
|------|------|--------|
| S1 注入 | ✅ 規則 ×2 | eslint no-raw-sql + CI grep |
| S2 反序列化 | ⚪ 本棧不適用(無動態求值 API) | — |
| ...   | ...  | ... |
```

**驗收門檻**:16 維全部有結論 · 每條 P0 都有可跑的執法指令 ·
每條 P0 都有出處連結與查證日 · CI-fail 清單存在且與內文 P0 一一對得上。

最後一步:把新附件的檔名加進 `setup.sh` 的 `STACK_FILES`,否則它是孤兒 ——
**規則與接線同一個 commit**。`scripts/check-docs-wired.sh` 會擋住忘記這一步。
